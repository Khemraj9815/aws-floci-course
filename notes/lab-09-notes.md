Lab 09 Notes
========

**compare two trust policies**

usms-ec2-app-role trusts a service principal (ec2.amazonaws.com): no person ever assumes it; EC2 obtains short-lived credentials on the instance's behalf and hands them to code on the instance through the metadata service. usms-developer-role trusts an AWS principal (an IAM user or the account): a person who already holds credentials calls sts:AssumeRole deliberately, so who obtains the credentials depends on which human identities the trust names, and how depends on their own keys or MFA.

**Step 6 - transcript actions**

Display a transcript (enrolment API): s3:GetObject on arn:aws:s3:::<bucket>/*, plus s3:ListBucket on arn:aws:s3:::<bucket> if it lists a student's files or needs a clean "not found" (without ListBucket, S3 returns 403 instead of 404 for a missing key). Upload a transcript (registry): s3:PutObject on /* (and usually s3:ListBucket and s3:GetObject to check what is already there). The one action only in the second list: s3:PutObject. That single action is why the read-only policy and role exist.

**1. Step 18: five scripts reported exactly what they had before.**
That is strong evidence because each script checks dozens of properties of a different earlier lab, so an unchanged result shows this lab's security changes broke nothing those labs depend on: a regression test written before the change, not after it. A plausible change that would break one: if Step 13's egress on `usms-enrolment-sg` had omitted the S3 prefix list and HTTPS, the ECS tasks could no longer pull images or write logs, and a `verify-lab-04.sh` check on running tasks would fail. I would read the diff to find the failing check, decide whether the old expectation is still right, and if so restore the missing rule from the undo document; if the architecture deliberately changed, update the check in the same commit (as Lab 05 Exercise 2 did).

**2. Attaching `USMSPermissionsBoundary` with `attach-role-policy`.**
Attached as an ordinary policy, the boundary's **Allow** statements (if any) become grants, so the role may gain permissions it never had, and the boundary no longer caps anything, because the role has no boundary set: effective permissions go **up** in both senses (more grants, no ceiling). Its explicit **Deny** statements still apply, so the role loses the IAM-changing actions the boundary denies: they go **down** for those. It becomes dangerous when the role can create or modify other roles, because nothing then stops it escalating. Section 8's check that the boundary policy is attached to **no** entities (`list-entities-for-policy` returns nothing) and that `usms-deploy-role` has a `PermissionsBoundary` set catches it.

**3. Every ingress rule correct, data still exposed.**
An attacker exploits a vulnerability in the enrolment API through the load balancer (allowed traffic on port 80), runs code in the task, uses the task role's `USMSStudentDataReadWrite` permissions to read transcripts from S3, and sends them to their own server over HTTPS. Step 13's egress narrowed it slightly: the stolen data can no longer leave on arbitrary ports or protocols, but tcp/443 to `0.0.0.0/0` still lets it out, so the narrowing is small. What would have prevented it entirely is an egress filter allowing only named destinations (AWS Network Firewall or a proxy), plus a read-only role for a service that only displays transcripts; the course cannot build the filter because Floci does not emulate Network Firewall and does not enforce security groups at all.

**4. Same trust, different permissions; different trust plus a boundary.**
`usms-ecs-task-role` and `usms-transcripts-reader-role` trust only `ecs-tasks.amazonaws.com`, with source conditions, so an attacker calling `sts:AssumeRole` from their own machine as an IAM principal is not the trusted principal, and AWS denies the call for both; their different permissions never come into play. `usms-deploy-role` trusts `usms-admin-01`, so the call succeeds **only** if the attacker holds `usms-admin-01`'s credentials; if they do, they get the deploy permissions but capped by the boundary, so they still cannot change identities or pass roles to EC2. The answers differ because a service trust admits no human caller at all, while a user trust admits whoever holds that user's keys, which is why key rotation and MFA matter for it.

**5. Five controls on `usms-db-01` versus one on `usms-enrolment-sg`.**
Not five times better: controls only multiply protection when they fail independently. Several of the five share a failure mode: "no public IP", "no auto-assign" and "no IGW route" all fail together if someone moves the instance to a public subnet, while the security group and NACL are separate. The enrolment tasks are protected by fewer controls by count, but they also have no public IPs, sit in private subnets with no IGW route, and only admit the ALB's group; Step 17's matrix models only security groups, so it reports them as a "single point of control" when the routing layer is actually protecting them too. The honest conclusion is that both are reasonably protected, and the matrix undercounts controls it does not model.

**6. The two extra rotation steps.**
Repointing the profile and **verifying it before** touching the old key protects against locking yourself out: if the new key were broken or mistyped, deleting the old one first would leave no working credentials (an outage of your own access). **Deactivating before deleting** protects against an unknown consumer: if some script or server still used the old key, deactivation makes it fail visibly but reversibly, so you can reactivate, find it and move it; deleting first would break it permanently. A long-lived key is a compromise because anyone who copies it once (a leaked repo, a log, a laptop) can use it until someone notices, with no expiry. Humans should use federated, short-lived access through IAM Identity Center with MFA; workloads should use roles (instance profiles, task roles, IRSA), which issue temporary credentials automatically.

**7. Reading versus testing.**
Reading is not a full substitute, but it is a necessary one. Reading catches defects that tests miss because they are *permissions you have not thought to test*: for example, a `Resource: "*"` on `s3:PutObject` that no test exercises because every test uses the intended bucket. Testing catches defects reading misses because they depend on *how AWS evaluates* the document: for example, a condition key the service never sends (EC2 and `aws:SourceArn`), which reads correctly but silently never matches, or a `NotPrincipal` deny that blocks assumed-role sessions. For student transcripts I want reading first (it is fast, finds over-broad grants before anything runs, and can be done here), then testing on real AWS before any real data is stored.
